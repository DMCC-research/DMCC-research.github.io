在 2026-06-29 至 2026-07-05 期间，最显著的信号是，AI 基础设施论文正将上下文、KV 缓存、检索载荷和持久化智能体记忆呈现为可调度的数据对象。它们的共同机制不只是加快推理服务，而是决定哪些数据应留在近处、哪些应以紧凑形式移动，以及哪些根本不应移动。

## KV 缓存 | 智能体推理服务越来越像驻留管理

[TraceLab](https://arxiv.org/abs/2606.30560) 围绕长上下文、短输出交互、工具调用延迟、前缀缓存命中率，以及由人类交互节奏决定的缓存访问间隔，刻画了编程智能体的工作负载。这些特征的组合之所以重要，是因为编程智能体处理的并非彼此孤立的聊天请求；在工具或人类造成的延迟之后，它们会反复回到代码仓库上下文、工具输出和先前的交互状态。

这对基础设施的启示是，应将前缀缓存作为一种驻留机制来评估，而不只是将其视为命中率优化手段。编程智能体循环中的一次前缀缓存未命中，可能迫使提示词 token、工具上下文和重建的 KV 状态重新进入延迟敏感路径；TraceLab 对智能体工作负载中可复用的长上下文和缓存访问间隔的关注，也提示了这一点 [TraceLab](https://arxiv.org/abs/2606.30560)。

我的判断是，编程智能体推理服务需要一种更接近“跨间隔的有效驻留”的指标，而非总体每秒 token 数。对于这一研究方向，重要的问题是推理服务栈能否在工具调用和人类思考期间，让合适的前缀和 KV 状态保持可快速复用，而不只是能否快速处理单个请求 [TraceLab](https://arxiv.org/abs/2606.30560)。

## 内存层级 | KV 传输成为显式的推理服务操作

[HBM 并非你所需的全部](https://arxiv.org/abs/2606.29986) 围绕内存异构加速器、预填充与解码分离、针对阶段专门设计的加速器、量化 KV 传输、延迟反量化，以及每美元有效吞吐量来构建 LLM 推理服务框架。其中有用的抽象是，预填充和解码对内存、带宽及延迟的要求并不相同。

这对数据移动的启示很直接：KV 缓存不再只是单个加速器内部的临时注意力状态。在 HMA-Serve 的框架中，KV 可以先压缩以便传输，在异构内存层级之间移动，再在接近使用位置的地方进行反量化 [HBM 并非你所需的全部](https://arxiv.org/abs/2606.29986)。

这指向了一类推理服务策略：将 HBM 视为稀缺的热数据层，而不是所有推理服务状态的默认存放位置。尚待解决的系统问题是，在将尾延迟、KV 迁移量和运维复杂性纳入考量后，针对阶段专门设计的异构加速器能否优于更简单的内存池化方案 [HBM 并非你所需的全部](https://arxiv.org/abs/2606.29986)。

## 检索 | 获取数据成为有条件的移动

[获取之前先判断](https://arxiv.org/abs/2606.29959) 研究了 RAG 中经过校准的检索预算分配，包括闭卷门控、自适应检索预算，以及 token 数与延迟之间的前沿。其机制相当于检索侧的 KV 放置策略：只有当不确定性足以证明成本合理时，才移动外部上下文。

这一点很重要，因为检索会让数据流经多个阶段：查询处理、索引访问、文档获取、重排序、提示词插入，以及生成过程中的 KV 扩展。经过校准的检索预算将这些步骤转化为有条件的数据移动决策，而非固定采用 top-k 的惯常做法 [获取之前先判断](https://arxiv.org/abs/2606.29959)。

面向生产环境的方向是，不只用提示词 token 数来报告检索成本。对于以数据移动为核心的系统，相关的权衡前沿应涵盖针对特定查询的预算下的存储/索引访问、文档字节数、新增上下文 token 数、延迟和准确率 [获取之前先判断](https://arxiv.org/abs/2606.29959)。

## 智能体记忆 | 持久化经验移出提示词

[经验图谱](https://arxiv.org/abs/2606.29823) 为自我改进的智能体提出了持久化、可查询的经验图谱，支持跨会话复用、时间旅行查询和无状态智能体计算。其机制将智能体的长期记忆从向提示词中堆塞内容，转向外部数据底座。

这对基础设施的启示是，智能体记忆成为一个存储与检索设计问题。系统必须决定哪些内容保留在即时上下文中、哪些内容被摘要化、哪些内容建立索引、哪些内容进行版本管理，以及哪些内容被检索回当前运行过程 [经验图谱](https://arxiv.org/abs/2606.29823)。

这与前缀缓存互为补充，而不是替代关系。前缀缓存优化的是推理服务循环中近期反复使用的上下文，而经验图谱面向的是持久化的跨会话复用和历史可查询性 [TraceLab](https://arxiv.org/abs/2606.30560)、[经验图谱](https://arxiv.org/abs/2606.29823)。

## 近数据计算 | 减少移动仍需仲裁

[COSM](https://arxiv.org/abs/2606.30553) 研究了移动设备上 PIM 与 CPU 并发执行的协同调度，关注共享内存争用、存储体冲突、总线拥塞、空闲感知调度和 PIM 命令插入。这篇论文的价值在于，它避免了“将计算移到内存附近就能自动解决数据移动问题”这一过于简单的论断。

近数据执行可以减少片外数据移动，同时也可能加剧内存系统内部的争用。对于 LPDDR 带宽和能耗均受约束的移动端 AI，调度器必须在将 PIM 工作插入内存系统可用空闲时隙的同时，保持 CPU 的响应能力 [COSM](https://arxiv.org/abs/2606.30553)。

更广泛的启示是，近数据计算首先是一种调度机制，然后才是硬件层面的收益。需要关注的瓶颈不只是 PIM 峰值吞吐量，还包括存储体、总线与 CPU 需求之间的仲裁 [COSM](https://arxiv.org/abs/2606.30553)。

## 推理服务 QoS | 能耗控制随数据阶段而变

[Festina](https://arxiv.org/abs/2606.30391) 面向共享 GPU 上无服务器 LLM 推理服务的能耗感知调度，采用阶段感知调度、SM 分区、GPU 工作点、SLO 感知整合，以及静态功耗削减。它与数据移动的联系在于，不同推理服务阶段以不同方式持有和转换驻留内存的状态。

预填充、解码、KV 复用、驱逐和整合，不应隐藏在单一的“GPU 请求”抽象背后。SLO 感知整合可能降低静态功耗，但也可能改变内存带宽、缓存容量和 KV 驻留方面的争用 [Festina](https://arxiv.org/abs/2606.30391)。

在研究报告中，每个有效 token 的焦耳数应与内存压力的可观测性配套呈现。当能耗结果揭示了带来节能效果的推理服务阶段、驻留状态和 SLO 权衡时，这些结果就更具实践指导价值 [Festina](https://arxiv.org/abs/2606.30391)。

## 结论

本周的方向很明确：AI 推理服务系统正开始围绕数据阶段进行专门化设计。KV 缓存、前缀、检索到的文档、工具输出和持久化智能体记忆，都需要明确的驻留、压缩、迁移、检索和驱逐策略。下一步有价值的研究工作是将测量指标标准化，例如每个有效 token 对应的数据移动字节数、跨时间间隔的 KV 驻留情况、每个正确答案对应的检索字节数，以及内存压力可观测条件下的能耗。
