在 2026-07-20 至 2026-07-26 期间，推理服务系统方面最强烈的信号是：运行时状态正从实现细节转变为显式的架构对象。KV 缓存、多模态载荷、检索集合、智能体轨迹、检查点、本地记忆和模型张量，如今都需要各自的放置、复用、隔离和恢复策略。

## KV 缓存 | 优化与治理交汇

[Windowed-MTP](https://arxiv.org/abs/2607.21535) 针对多 Token 预测式推测解码中的草稿 KV 开销，用有界窗口、注意力汇聚点和环形缓冲区 KV 回收机制取代草稿模型的全上下文注意力。其机制很直接：即使目标模型的上下文扩展至接近百万 Token 的规模，也让草稿模型的活跃 KV 工作集保持恒定。这对推理服务的启示是，推测解码不只是一种计算优化；它也成为运行时内部的缓存组织问题。

[KV 缓存驱逐的误差证书](https://arxiv.org/abs/2607.21475) 采用了不同的视角：如果输出在 KV 驱逐后发生变化，推理服务系统就需要证据来判断失败是否由驱逐导致。其随机化驱逐设计、泊松采样的尾部、Hájek 校正和重计算调度，将缓存驱逐界定为归因问题，而非简单的内存压力启发式策略。这很重要，因为生产系统往往需要知道质量下降究竟来自模型、提示词、检索、量化，还是推理服务策略。

[HeadCast](https://arxiv.org/abs/2607.20125) 提出了另一个维度，认为自回归视频生成可以采用针对不同注意力头的 KV 路径。其主张是，注意力头承担着不同的时间角色，因此统一的缓存保留策略可能浪费内存或损害生成质量。如果这一结果在已评估的场景之外仍然成立，KV 策略就需要更加贴合模型结构：缓存管理的单位可能是注意力头、层、请求、租户或模态，而不只是 Token 位置。

[HijackKV](https://arxiv.org/abs/2607.19957) 将 KV 复用变成了一道安全边界。其与位置无关的 KV 复用威胁模型指出，复用的缓存状态可能携带上下文，从而使投毒或跨请求泄漏成为可能。这是本周 KV 相关进展中不可回避的约束：只有当运行时也能表达隔离、所有权和位置语义时，复用才有价值。

原创判断：如今，KV 缓存不应再主要被视为私有张量缓冲区，而应更多地被视为受管理的内存子系统。当前缺失的抽象是一个 KV 控制平面，能够表达保留、驱逐归因、重计算回退、复用资格和租户隔离，而无需让每个模型或推理服务引擎以临时拼凑的方式编码这些策略。

## 多模态上下文 | 成本前移至注意力计算之前

[ReMo](https://arxiv.org/abs/2607.21179) 提出，通过对齐音视频嵌入，并用文本代理表示替换冗余的视觉上下文，减少全模态 LLM 的跨模态冗余。其推理服务机制是在主模型处理多模态载荷之前降低输入 Token 成本。这将工作从生成阶段转移到准入阶段：决定哪些视觉或音频 Token 值得以完整表示呈现给模型。

[SmartVL](https://arxiv.org/abs/2607.20357) 通过 Token 与计算的联合自适应，明确提出了这一准入问题。视觉 Token 控制器和 LLM 计算控制器通过共享预算编码和可微延迟估计器进行协调。对基础设施的启示是，多模态推理服务需要围绕模型设置具备预算感知能力的控制器，而不只是扩大上下文窗口。

[Fusion Embedding](https://arxiv.org/abs/2607.18666) 指向了检索侧的同类压力：利用模态门控适配器，为文本、图像、视频和音频构建统一的嵌入空间。如果单一多模态索引取代相互独立的检索路径，推理服务系统就能减少编排开销，但也会承接一个新的调度问题：在解码、嵌入、存储和时效性成本各不相同的模态之间选择证据。

[REFACT](https://arxiv.org/abs/2607.20833) 通过自适应事实重述和引用效用奖励，将中间推理上下文视为可压缩状态。它与推理服务的关联不只在于思维链这一框架，还在于这样一种理念：承载证据的中间状态可以被压缩，同时保留与答案相关的事实。

这些工作的共同机制是上游载荷削减。在昂贵的注意力计算路径开始之前，多模态工作负载就已通过媒体解码、嵌入、检索、Token 化和上下文构建给推理服务系统带来压力。因此，一个实用的推理服务栈需要多模态准入层：在证据重要时保留其完整保真度，在冗余载荷无关紧要时用代理表示替代，并显式呈现这种压缩带来的质量风险。

## 智能体运行时 | 工作流状态成为服务单元

[AgentTrails](https://arxiv.org/abs/2607.18816) 将智能体任务建模为溯源图，其中工具调用是计算动作，产物是依赖项。这将智能体服务重新定义为持久化工作流执行：平台必须跟踪调用了什么、生成了什么、哪些可以复用，以及哪些必须重新计算。

[BioSecBench-Surveillance](https://arxiv.org/abs/2607.19262) 给出了一种具体的工作负载形态：智能体处理病原体基因组监测工作流，涉及原始测序数据、参考序列选择、确定性评分，以及阈值或归一化错误。对推理服务的启示是，智能体可靠性取决于流水线状态和领域产物，而不只是语言模型的下一 Token 行为。

[AgentDebugX](https://arxiv.org/abs/2607.18754) 强调轨迹诊断、根因归因、恢复和重跑。[ResearchArena](https://arxiv.org/abs/2607.19321) 强调自动化研究工作流中的蓄意破坏与监控。[了解你的智能体](https://arxiv.org/abs/2607.19837) 围绕黑盒探测、智能体画像、知识资产和间接提示注入，构建侦察驱动的渗透测试框架。[智能体应用中的数据泄漏防护](https://arxiv.org/abs/2607.18847) 聚焦于收紧模式约束、边界净化、基于允许列表的工具准入控制，以及最小权限检查。

这些论文共同表明，智能体服务平台需要的不只是请求日志。它还需要可重放的轨迹、产物存储、凭据边界、工具策略和恢复钩子。延迟的构成也随之改变：服务耗时包括检索、沙箱启动、工具 I/O、验证和重跑。

[SetwiseEvalKit](https://arxiv.org/abs/2607.19747) 和 [SciExplore](https://arxiv.org/abs/2607.20926) 在工作流层面增加了检索压力。载荷不是一篇检索到的文档，而是一个经过选择、必须支持跨文档或跨来源协调的证据集合。这使检索调度成为智能体服务的一部分，而非预处理细节。

## 冷启动 | 参数搬移仍是痛点

[InstantInfer](https://arxiv.org/abs/2607.18957) 是本周数据中心推理服务方面最明确的信号。它使用通信有限自动机对推理服务组件进行建模，以改善 LLM 冷启动，并将张量加载和模型切换视为首要瓶颈。硬件层面的问题是，参数在使用之前位于何处：GPU HBM、CPU DRAM、本地 NVMe、网络存储，还是对象存储。

随着推理服务集群日益异构化，这一点愈发重要。智能体可能调用多个模型、适配器、检索器、工具运行时和验证模型。当突发负载的主要开销来自参数搬移和运行时初始化时，仅优化稳态解码吞吐量的平台仍可能表现不佳。

## 边缘推理服务 | 本地记忆即基础设施

[HiMe](https://arxiv.org/abs/2607.21019) 围绕可穿戴设备数据的实时摄取、作为核心组件的数据库，以及长期用户建模，构建自托管健康智能体。[RUMBA](https://arxiv.org/abs/2607.21447) 通过带时间戳的对话 QA，评估会话内和跨会话的用户记忆。[无需云端的智能体编程](https://arxiv.org/abs/2607.21482) 则加入了本地性约束：敏感数据或受治理要求限制的数据，可能促使智能体编程工作负载迁移到本地或消费级硬件上。

推理服务面临的问题不只是将更小的模型放到边缘端，而是将持久的用户记忆与短暂的推理状态分离。本地智能体需要存储策略、隐私边界、检索时效性，以及跨 CPU、GPU、NPU、DRAM、本地磁盘和受电池约束设备的资源感知调度。

## 架构方向

本周的证据指向一个生产实践和研究方向：状态生命周期调度。面向此类工作负载的推理服务栈，需要一个管理类型化缓存状态的 KV 管理器、一个削减载荷的多模态准入层、一个支持溯源与恢复的智能体执行底座，以及一个同时对参数搬移和运行时状态搬移进行建模的放置调度器。

FLOPs 仍然重要，但本周的论文提出了一个更具体的观点：高效的 AI 推理服务越来越依赖于控制哪些内容需要搬移、哪些需要持久保留、哪些可以复用，以及哪些必须隔离。接下来有价值的系统研究成果，很可能来自将这些策略显式化，使其足以支持调度、审计，以及与硬件的协同设计。
