从 2026-06-29 到 2026-07-05，AI 推理服务领域最强烈的信号是：生产环境中的推理服务，与其说是在执行彼此孤立的请求，不如说是在持续管理有状态的计算。编程智能体轨迹、异构 KV 缓存推理服务以及智能体记忆论文，都指向同一个系统问题：哪些状态应保持热驻留，哪些状态应迁移，以及谁拥有这些状态？

## 编程智能体 | 前缀复用遇上人类交互节奏

[TraceLab](https://arxiv.org/abs/2606.30560) 是本周的核心工作负载论文，因为它从长上下文、短输出行为、工具调用延迟、前缀缓存复用以及按人类节奏产生的轮次间隔等方面，刻画了编程智能体的推理服务特征。这一点很重要，因为 Claude Code 和 Codex 等编程智能体并非只是发送一次提示并接收一次补全；它们会反复让工作区状态、工具输出、部分计划和长前缀流经推理服务路径。

其机制很直接：较长的用户前缀或工作区前缀会被转换为 KV 缓存，只有下一轮与先前前缀的匹配程度足够高时才能复用，也只有缓存在工具调用延迟和用户思考时间内未被淘汰时才能保留下来。[上下文腐化研究](https://arxiv.org/abs/2606.29718) 进一步指出，随着上下文累积，长程搜索质量可能下降；而 [SpreadsheetBench 2](https://arxiv.org/abs/2606.29955) 则在办公工作流中展示了同样的模式：智能体必须在整个工作流中保留多工作表的工作簿状态以及针对目标单元格的操作意图。

这对基础设施的启示是，评估前缀缓存时，应将请求到达间隔、工具调用延迟和淘汰压力纳入考量。若基准测试使用连续紧接的合成轮次来测量前缀缓存命中率，就很可能高估它对编程智能体和办公智能体在生产环境中的价值。

## KV 所有权 | 异构推理服务需要显式状态对象

[HMA-Serve](https://arxiv.org/abs/2606.29986) 主张在内存异构的加速器之间实现解耦式 LLM 推理服务，采用针对不同阶段专门优化的加速器、量化 KV 传输、延迟反量化以及预填充/解码解耦。一篇关于[异构 LLM 推理与服务](https://arxiv.org/abs/2606.29708)的配套设计空间论文明确提出了更精准的抽象：KV 所有权、KV 表示形式、计算放置、精度策略和驻留位置，都是首要设计选择。

其推理服务机制在于，预填充和解码对系统造成的压力不同。预填充处理长输入，对计算和内存带宽的需求很高；解码则对延迟敏感，并且会反复访问 KV 状态。只有当 KV 迁移、互连压力和精度转换不会抵消利用率收益时，解耦才有帮助。[HSAP](https://arxiv.org/abs/2606.30460) 虽然围绕混合上下文生成模型展开，但也通过打包序列处理、序列感知并行和通信优化，强化了同样的关注点。

我的判断是，KV 缓存应被视为调度器可见的对象，而非由某个工作进程私有持有的附带张量。一个实用的推理服务架构应按模型、层、会话、精度、驻留层级和复用价值跟踪 KV 对象，然后决定保留、压缩、迁移还是淘汰它们。这正是编程智能体轨迹与异构推理服务硬件之间缺失的接口。

## 智能体记忆 | 溯源信息成为推理服务元数据

[VISTA](https://arxiv.org/abs/2606.30005) 将 LLM 智能体定位为潜在的上下文管理器，并提出一个提供 token 用量可视性、带类型的可寻址记忆块以及全保真归档访问能力的仪表盘。[Experience Graphs](https://arxiv.org/abs/2606.29823) 提出持久、可查询的智能体状态，以支持跨会话复用。[DuoMem](https://arxiv.org/abs/2606.29961) 通过上下文空间和参数空间蒸馏探索端侧记忆智能体，而 [Neural Procedural Memory](https://arxiv.org/abs/2606.29824) 则探索将隐式激活引导作为另一种智能体记忆形式。

这些论文区分了推理服务系统经常混为一谈的四类状态：热 KV 与提示状态、温会话状态、持久可查询记忆，以及参数化记忆或激活层面的记忆。每一类都有不同的迁移和治理成本。热 KV 需要加速器内存带宽；会话状态需要低延迟序列化；持久记忆需要查询、保留和访问控制；参数化记忆减少了提示传输量，但使模型版本管理和更新放置更加复杂。

[MemLeak](https://arxiv.org/abs/2606.29788) 通过溯源图、残留记忆、以图像为媒介的泄漏以及语义删除，研究多模态智能体记忆中的信息泄漏，使这一问题的隐私层面变得具体。因此，删除并不只是执行一次数据库删除操作。如果一条数据已被转换为图像、嵌入、摘要、提示、KV 缓存条目或生成的记忆，推理服务栈就需要具备跨这些表示形式的溯源能力。

## 调度 | 利用率作为控制信号过于粗糙

[Festina](https://arxiv.org/abs/2606.30391) 研究共享 GPU 上无服务器 LLM 推理服务的能耗感知调度，采用阶段感知调度、SM 分区、GPU 工作点控制、SLO 感知整合以及静态功耗降低等方法。关键机制在于，预填充和解码对计算、内存带宽及延迟预算的消耗组合不同，因此，对共享加速器而言，按请求数量调度过于粗糙。

在边缘侧，[COSM](https://arxiv.org/abs/2606.30553) 研究移动设备上 PIM 与 CPU 并发执行的协同调度，重点关注共享内存争用、存储体冲突、总线拥塞、空闲感知调度以及 PIM 命令插入。这里的瓶颈并不是抽象的加速器槽位，而是严格功耗约束下的共享 DRAM 和总线时序。

综合来看，这些论文表明，推理服务调度器需要能够观察执行阶段与资源争用。在数据中心，这意味着围绕预填充、解码、KV 驻留以及互连上的数据迁移进行调度。在设备上，这意味着围绕 CPU、PIM、NPU、DRAM、存储和功耗状态之间的交互进行调度。

## 工具运行时 | 推理服务延伸至 GPU 之外

[MCP 服务器架构模式](https://arxiv.org/abs/2606.30317) 讨论了集成 LLM 的应用中的资源网关、工具编排器、有状态会话服务器、传输开销以及工具选择性能退化。[MESA](https://arxiv.org/abs/2606.30602) 研究多智能体系统中易受攻击的通信通道，而 [Linguistic Firewall](https://arxiv.org/abs/2606.30555) 则探索针对元数据注入的路由防御。[COHORT](https://arxiv.org/abs/2606.30479) 通过在仿真拓扑上开展协同攻击重放，又提供了一种高度依赖编排的工作负载。

这里的推理服务机制发生在 GPU 之外：工具模式定义进入模型上下文，工具输出作为新的上下文或记忆返回，智能体消息沿图中的边传递，而会话状态可能存在于 MCP 服务器、编排器、数据库或提示中。如果工具调用主导了实际经过时间上的延迟或上下文增长，那么仅优化模型执行就会错过生产环境中的瓶颈。

## 结论

研究方向是构建具有显式状态平面的推理服务栈：KV 缓存、前缀缓存、工具输出、持久记忆、溯源记录和参数化记忆，都应对调度和可观测性机制可见，而非隐藏在应用层文本组装之后。近期最重要的实验是，将 [TraceLab](https://arxiv.org/abs/2606.30560) 中的编程智能体工作负载轨迹，与 [HMA-Serve](https://arxiv.org/abs/2606.29986) 和[异构推理设计空间论文](https://arxiv.org/abs/2606.29708)中的异构 KV 推理服务设计结合起来，然后衡量在按人类节奏发生的缓存复用和真实淘汰压力下，预填充/解码解耦是否仍能带来收益。
